# Randonneurs Ontario — Codebase Audit

Stack: Next.js 16 (App Router) + React 19 + TypeScript + Supabase (Postgres) + AWS SES + Sentry + Vercel + GitHub Actions cron. Auth: Supabase email/password for admins; capability-token URLs for unauthenticated rider self-service.

---

## Executive summary

**Overall risk: Medium.** The codebase is unusually well organized for a volunteer-run project: docs are current, the data layer cleanly separates reads/writes, RLS is on, capability tokens are hidden from anon, and there's a real test suite. But three structural issues raise the risk level:

- **Biggest security concern:** `chapter_admin` is documented as chapter-scoped, but no server action enforces the scope. All write paths use the service-role client and only call `requireAdmin()`. A Toronto chapter admin can mutate Ottawa events, routes, results, riders, news, pages, and navigation. (See finding #1.)
- **Biggest correctness concern:** ACP results emails are hardcoded to `leissp@mac.com` and CC `vp-toronto@randonneursontario.ca` regardless of which chapter ran the event (`lib/actions/events.ts:647-651`). Ottawa/Huron/Simcoe submissions silently route to Toronto.
- **Biggest performance concern:** The event registration server action awaits the CCN HTTP call (10s timeout) before returning to the user on every registration, with no caching of failure results — a slow CCN morning grinds the registration form to a halt.
- **Biggest maintainability concern:** `next.config.ts:66` sets `typescript.ignoreBuildErrors: true`. Combined with no CI for typecheck/lint/test (only a husky pre-push hook), broken types ship to production. The pre-push hook can be bypassed and doesn't run in cloud editing.
- **Fastest high-leverage improvement:** Add a CI workflow (typecheck + lint + `npm run test:run`) on every PR. It would have caught most of the issues here and removes the pre-push hook as a single point of failure.

## Top 10 findings

### 1. Chapter-admin authorization is not enforced in server actions

- **Category:** Security / Reliability
- **Severity:** Critical
- **Confidence:** Confirmed
- **Location:** `lib/actions/events.ts:78`, `routes.ts:104`, `results.ts:82,147,206,291,361,421`, `riders.ts`, `news.ts:26`, `navigation.ts:39`, `pages.ts:55`, `awards.ts`, `manage-registration.ts` (admin paths)
- **What I found:** Every admin action calls `requireAdmin()` (which returns any admin role) and then writes through `getSupabaseAdmin()` (service-role, bypasses RLS). Nothing checks `admin.chapter_id` against the resource's `chapter_id`. The RLS policy `is_chapter_admin(check_chapter_id)` (`supabase/migrations/20260107011913_add_rls_policies.sql:32`) is correct but never executes because the service-role key skips RLS.
- **Why it matters:** `docs/SECURITY.md` advertises `chapter_admin` as chapter-scoped; the role exists in the DB and is assigned by super_admins; but the application enforces the same privilege as `admin`. Any chapter admin can wipe another chapter's events, edit news/pages/navigation, or alter results. This is a silent privilege model mismatch — exactly the class of bug that audit logs alone won't prevent.
- **Recommended fix:** Introduce `requireChapterAdmin(chapterId)` (and a `requireFullAdmin()` for org-wide actions). Plumb resource → chapterId resolution into each action. Add integration tests that assert a chapter_admin in chapter A cannot mutate chapter B resources.
- **Effort:** Medium
- **Owner:** Backend

### 2. TypeScript build errors are silenced

- **Category:** Reliability / DX
- **Severity:** High
- **Confidence:** Confirmed
- **Location:** `next.config.ts:66` (`typescript: { ignoreBuildErrors: true }`)
- **What I found:** Production builds skip type checking. There's also no GitHub Actions workflow for typecheck/lint/test (`.github/workflows/` only has the cron job). The husky pre-push hook (`.husky/pre-push`) runs `tsc --noEmit && npm run test:run`, but it can be bypassed with `--no-verify` and doesn't run for browser-based commits or fork PRs.
- **Why it matters:** Combined with the pervasive `as` casts noted below, this lets type drift ship.
- **Recommended fix:** Remove `ignoreBuildErrors`. Add a single `.github/workflows/ci.yml` that runs typecheck, lint, and `test:run` on PRs and `main`. Fix any errors that surface.
- **Effort:** Small (workflow); Medium (clearing latent errors)
- **Owner:** Infra / Full-stack

### 3. PostgREST filter injection via fuzzy rider search

- **Category:** Security
- **Severity:** High
- **Confidence:** Likely (verify behavior)
- **Location:** `lib/actions/rider-match.ts:78,94`
- **What I found:** The public, anonymous server action `searchRiderCandidates` builds a PostgREST `or()` filter by string-concatenating a normalized first-name variant: `firstNameVariants.map(v => \`first_name.ilike.%${v}%\`).join(',')`. `getNameVariants()`lowercases and trims but does not strip commas, parentheses, or PostgREST operator characters. PostgREST's`or`syntax delimits filters by`,`. The query runs through `getSupabaseAdmin()`(service-role) against`riders`, which contains email and emergency contact columns.
- **Why it matters:** A registrant entering a first name like `bob,email.like.%@target.com%` may inject an additional filter expression, potentially enumerating riders by email or emergency contact. Even if exploitation is bounded, the input is anonymous and reachable from the public registration form.
- **Recommended fix:** Sanitize by either (a) keeping only `[a-z]` after lowercasing in `getNameVariants`, or (b) replacing the manual `or()` string with explicit parameterized calls or an RPC. Add a regression test that names containing `,`, `(`, `)`, `*`, `:` are either rejected or escaped.
- **Effort:** Small
- **Owner:** Backend

### 4. ACP results email hardcoded to one Toronto recipient

- **Category:** Product correctness
- **Severity:** High
- **Confidence:** Confirmed
- **Location:** `lib/actions/events.ts:647-651`
- **What I found:** `submitEventResults` sends ACP homologation emails to `'leissp@mac.com'` with CC `[admin.email, 'vp-toronto@randonneursontario.ca']` for _every_ chapter. The TODO comment says "change to vp-admin@randonneursontario.ca when someone other than Peter handles the admin emails."
- **Why it matters:** Submissions for Ottawa, Huron, and Simcoe-Muskoka events go to the Toronto VP and one personal Gmail-style address. Misroutes ACP homologation. Single point of failure if Peter changes email.
- **Recommended fix:** Read recipient from chapter config (extend `lib/email/vp-emails.ts` to include the homologation address per chapter), or move to a single role-based mailing list. Remove the personal address.
- **Effort:** Small
- **Owner:** Product / Backend

### 5. Synchronous CCN membership check on every registration

- **Category:** Performance / Reliability
- **Severity:** High
- **Confidence:** Confirmed
- **Location:** `lib/memberships/service.ts:64`, `lib/ccn/client.ts:43-72`, called in `lib/actions/register.ts:514,891,1245`
- **What I found:** Every registration that doesn't already have a non-Trial membership row hits the CCN HTTP API with a 10-second timeout. CCN's first response is awaited inline before the registration row is created. There's no negative caching: if CCN is slow or down, every fresh registrant pays the latency.
- **Why it matters:** Brevet registration windows are bursty (rides open hours fill up quickly). A slow CCN makes the form feel broken, encourages refresh-spam, and serializes through Vercel's per-region instances even when the user has nothing in CCN.
- **Recommended fix:** (a) Cache "no membership" lookups in `rider_memberships` for a short TTL (e.g., 1 hour) so retries don't repeatedly call CCN; (b) shorten timeout to ~3s and surface a friendly "we couldn't verify yet — registration accepted, please join the club" path; (c) fail open by creating the registration first (status `incomplete: membership`), then verify async. The "incomplete: membership" status already exists, which makes this refactor cheap.
- **Effort:** Small–Medium
- **Owner:** Backend

### 6. Storage bucket policies grant write to any authenticated Supabase user

- **Category:** Security
- **Severity:** Medium-High
- **Confidence:** Likely (depends on prod auth config)
- **Location:** `supabase/migrations/20260111022059_add_image_storage.sql:23-44`
- **What I found:** The `images` bucket allows INSERT/UPDATE/DELETE to any role with `auth.role() = 'authenticated'`. The same `images` table has policies based on `auth.role() = 'authenticated'` rather than `is_admin()`. `supabase/config.toml` (local) keeps `enable_signup = true`. Production may differ, but if signup is enabled in production Supabase Auth, anyone can sign up via the GoTrue API with the public anon key and then upload to a public-read CDN bucket the project depends on.
- **Why it matters:** Public storage of arbitrary images is an abuse surface (illegal/copyrighted content hosted on the project's CDN domain). The protection here is not the storage policy but the existence/absence of signup in the remote project — an out-of-band switch with no test coverage.
- **Recommended fix:** Verify production has `enable_signup = false` (or replace the `auth.role()` policy with `is_admin()`). The `rider-submissions` bucket already uses the safer "writes via service role only" pattern (`20260324120000_restrict_rider_submissions_insert.sql`); apply the same here.
- **Effort:** Small
- **Owner:** Backend / Infra

### 7. Migration rolled back a token-hiding fix and the prod state of grants is opaque

- **Category:** Reliability / Security
- **Severity:** Medium
- **Confidence:** Needs verification
- **Location:** `supabase/migrations/20260318170000_restrict_token_columns_from_anon.sql` followed by `20260318190000_fix_token_column_security.sql` followed by `20260324130000_hide_capability_tokens.sql`
- **What I found:** The first migration revoked anon column-level access to capability tokens. The second migration immediately reverted it (because column grants broke aggregate joins) by re-granting full SELECT. The third migration permanently fixed it via a `public_registrations` view. A fresh `supabase db reset` ends up correct, but if production was deployed at the rollback point, the tokens were briefly anon-readable; and operators can't tell from the repo alone whether each migration was applied (especially in environments where someone may have manually patched production).
- **Why it matters:** Capability tokens (management_token, submission_token) are the entire security model for unauthenticated rider self-service.
- **Recommended fix:** Run the regression tests in `tests/integration-real/token-column-security.test.ts` against production. Document migration baseline in `docs/database-setup.md`. Consider squashing the three-step migration sequence in a follow-up to remove the bait-and-switch from history.
- **Effort:** Small (verification)
- **Owner:** Infra

### 8. Fire-and-forget emails inside server actions

- **Category:** Reliability
- **Severity:** Medium
- **Confidence:** Likely
- **Location:** `lib/actions/register.ts:540,589,637,915,962,1002,1267,1312,1365`, `manage-registration.ts:216`
- **What I found:** Email sends are _not_ awaited (`.catch(...)` only). On Vercel Fluid Compute / serverless, when the action's response returns, the runtime is free to suspend the worker. The SES `client.send` retry loop in `lib/email/ses.ts:80-92` may run partially or not at all.
- **Why it matters:** Quiet failures look like "registered but no confirmation email" — a known support-ticket source. The retry logic is built but won't help if the runtime kills the worker.
- **Recommended fix:** Await the email send (typical SES round-trip is <500ms; well under server action timeouts). Or move email to a queue (`waitUntil(...)` from Vercel's SDK) so the runtime keeps the worker alive until it finishes.
- **Effort:** Small
- **Owner:** Backend

### 9. JSON-LD blocks use `dangerouslySetInnerHTML` with admin-controlled strings

- **Category:** Security
- **Severity:** Medium
- **Confidence:** Likely
- **Location:** `components/structured-data.tsx:32,87,110`
- **What I found:** Each `<script type="application/ld+json">` is rendered with `dangerouslySetInnerHTML={{ __html: JSON.stringify(data) }}`. `JSON.stringify` does not escape `</script>` sequences inside string values. `EventJsonLd` includes `name`, `description`, `location`, all sourced from the events table. There is also no Content-Security-Policy header (`next.config.ts` only sets X-Frame-Options, etc.).
- **Why it matters:** A privileged user (admin / chapter_admin) writing `</script><script>...` into an event description would inject arbitrary JS on the public event page. Combined with #1 (chapter scoping not enforced), the blast radius is wider than expected.
- **Recommended fix:** Replace with a small helper that does `JSON.stringify(data).replace(/</g, '\\u003c')`. Add a basic CSP header (`script-src 'self'` plus the few inline-script hashes Next.js needs).
- **Effort:** Small
- **Owner:** Full-stack

### 10. `pages.ts` builds YAML frontmatter via string templating

- **Category:** Maintainability / Reliability
- **Severity:** Medium
- **Confidence:** Confirmed
- **Location:** `lib/actions/pages.ts:84-93`
- **What I found:** `title:`, `description:`, `headerImage:` are dropped into a YAML frontmatter block as raw strings: `title: ${title}`. A title containing `:`, a newline, or starting with `-`/`{`/`[` will produce malformed or actively misleading YAML; gray-matter parses some of those into structured values.
- **Why it matters:** Admin-only attack surface, but it's a footgun: the page silently breaks (or worse, frontmatter is interpreted as additional fields). The same pattern would not pass a code review against a YAML-aware library.
- **Recommended fix:** Use `js-yaml`'s `dump()` or quote values explicitly with proper escaping. Add a unit test for titles containing `:`, `\n`, `'`, `"`.
- **Effort:** Small
- **Owner:** Full-stack

## Detailed findings

### Performance

- **Sequential N admin queries on the dashboard.** `app/admin/page.tsx:24-29,67-104` issues four `count: 'exact'` head queries in parallel (good) but then runs `getEventRiderCounts` over up to 10 events with two large IN-list reads of `registrations` and `results`. As `riders` and `results` grow, this materializes a lot of rows just to compute Set sizes. Move to an RPC that returns counts (`get_event_rider_counts` already exists per migration `20260309130000`). **Low-Medium impact, easy fix.**

- **Unbounded fetch in `getAllRiders`.** `lib/data/riders.ts:24` paginates 1000 rows at a time but loops forever — no upper bound. Currently fine (~few thousand riders), but the `/riders` page renders the full list as a directory. Consider a virtualised list or filter-first UX once the count crosses ~10k.

- **`getAllNews()` admin-side has no `.limit()`** (`lib/data/news.ts:36-49`). Low impact today.

- **`getRiderResults`** (`lib/data/results.ts:444`) does a single deeply nested join across results → events → chapters → result_awards → awards, then a separate query for season awards. This is fine for small per-rider result sets but each awards row triggers its own join in PostgREST; for a long-time rider with hundreds of results, page render hits ~hundreds of joined rows. Consider an RPC.

- **`uploadDirect` flow is good** — `lib/actions/rider-results.ts` correctly uses signed upload URLs to bypass the 4.5 MB serverless body cap. `next.config.ts:13` documents this. Keep.

- **Sentry tracesSampleRate `1.0` on the client** (`instrumentation-client.ts:19`). 100% of client routes are traced — fine for low-traffic, but worth lowering to 0.1 once Sentry costs matter.

### Security

- See top-10 findings #1, #3, #6, #7, #9.

- **`/results/submit/[token]` is not in `robots.txt`** (`app/robots.ts:11`). `/admin/` and `/registration/manage/` are disallowed but `/results/submit/` isn't. If a token URL leaks to an indexable place, Google may crawl it. Add the path. **Low.**

- **`getSafeRedirectUrl` allows any URL starting with `/admin`** (`app/admin/login/page.tsx:13-18`). `redirect=/admin\nset-cookie:foo` style payloads aren't possible because Next.js URL parsing strips control chars, but consider the stricter `/^/admin(/|$)/` regex to avoid `/admin-evil.com/...` style edge cases. **Low.**

- **`isRateLimited` is in-process and per-instance** (`lib/rate-limit.ts:9-12`). Documented. Acceptable given Vercel's edge protection, but the login limit (5/15min) is per Vercel instance — distributed bots bypass it trivially.

- **PII in `console.error`** logs (`lib/actions/register.ts:268,319,344,844`, `riders.ts:268-393`, `events.ts:401-699`). The error path explicitly bypasses `logError()` (which has `skipSentry`/PII safeguards). Vercel's runtime logs persist these. SECURITY.md's "never log PII" guideline is partly enforced. **Medium.**

- **`changePassword` requires re-auth via `signInWithPassword`** (`lib/actions/auth.ts:73-79`). This races with rate limiting (login key is the same email) — calling change password 5 times in 15 minutes can lock the user out of `/admin/login`. Use Supabase's `verifyPasswordChallenge` or track separately. **Low.**

- **Honeypot + BotID is well-implemented** for registration (`lib/actions/register.ts:374-380`). No similar defense on `searchRiderCandidates` (#3) or `cancelRegistration` (token-only).

### Maintainability

- **150+ inline type assertions** across `lib/actions/*` and `lib/data/*` (`as RegistrationWithRider`, `as EventForCronCompletion`, etc.). The generated `types/supabase.ts` exists, but query-shape types live in `types/queries.ts` and are kept in sync by hand. Pattern: `const typedX = result as ShapeType`. Each cast is a place where a schema change won't compile-fail. Consider using `select<...>()` with the supabase-js v2 typed query builder, or generating per-query types. **Medium.**

- **30+ raw `console.error` / `console.log`** (see above). Pick `logError()` or a logger; remove the rest.

- **Three near-identical "send confirmation email" pathways** in `register.ts` for the no-membership / trial-used / valid branches (`registerForEvent`, `registerForPermanent`, `completeRegistrationWithRider`). 1300+ lines, mostly copy-paste. Extract a `sendRegistrationOutcomeEmail` helper.

- **`REAL_CHAPTER_SLUGS = ['huron', 'ottawa', 'simcoe', 'toronto']`** (`lib/actions/register.ts:43`) is hardcoded but the same data lives in `lib/chapter-config.ts`. A new chapter or rename will silently bypass membership chapter scoping. Drive from the single source of truth.

- **`getChapters()` in `lib/actions/admin-users.ts:279`** has no admin check. Returns chapter list to anyone who imports the action; chapters are public so the data isn't sensitive, but it's mis-located in an admin-only module.

- **`docs/ro-stats.sqlite*` files (3 files) are committed** (`docs/ro-stats.sqlite`, `.sqlite-shm`, `.sqlite-wal`). Looks like an artifact from a one-off migration script. Ship binary state into the repo? Probably not. Move to `.gitignore` or `scripts/cache/`.

- **Unused workflow comment** (`docs/audit-log.md`, `docs/superpowers/`, `docs/plans/`) — confirm these aren't stale.

### Reliability and correctness

- See top-10 #1, #4, #5, #8.

- **`createEarlyResult` reuses `management_token` as `submission_token`** (`lib/actions/manage-registration.ts:319-326`). Documented but means a single capability secret unlocks both flows. Consider whether reset/regenerate flows preserve this property when a registration is cancelled and re-instated.

- **`isTrialUsed` queries can race with the registration that's about to be created** (`lib/memberships/service.ts:115-143`). Two simultaneous registrations from one trial member could both pass the check and both succeed. Low frequency, but worth a unique constraint or a transactional check.

- **Image upload extension whitelist** (`lib/actions/images.ts:222-225`) collapses to `'bin'` if no alphanumeric ext is found. Combined with allowing `.docx`/`.xlsx`/`.pdf` MIME types, a renamed extension (`malware.bin`) is possible — admin-only, low risk, but worth normalizing to a known extension per content-type.

- **`updateProfile` lets an admin set their own `chapter_id` to anything** (`lib/actions/auth.ts:99-138`). A super_admin can set themselves to a non-existent chapter; a chapter_admin can move themselves to a different chapter. Not exploited today (because chapter scoping isn't enforced — see #1), but is a privilege drift risk once #1 is fixed.

- **`createPendingResultsAndSendEmails` swallows email failures into `errors[]`** but reports `emailsSent` accurately (`lib/events/complete-event.ts:167-171`). The cron handler logs `errors`, but there's no retry — failed result-submission emails are lost. Document this in `docs/event-results-spreadsheet.md` or add a re-send admin tool.

- **Date-of-month rollovers in `registerForPermanent`**: `createTorontoDate(eyear, emonth - 1, eday - 1, 20, 0)` for the day-before-deadline relies on JS `Date.UTC(..., 0)` wrapping to the last day of the previous month — which it does. False-positive flag, kept for transparency.

### Architecture

- **`proxy.ts` is correct for Next 16** (the runtime renamed `middleware.ts` → `proxy.ts`). The matcher is hand-maintained — anyone adding a route under `/admin` is fine because the matcher is `/admin/:path*`.

- **No content-driven `app/admin/[chapter]/...` segmentation.** Admin pages don't take a chapter route param; chapter scope is implied by the admin's own `chapter_id`. Once #1 is fixed, this is a UX wart: a chapter_admin viewing `/admin/events` sees a list filtered server-side, but a super_admin viewing the same list has to multiplex chapters via filters. Worth a chapter switcher in the sidebar.

- **GitHub-as-CMS for `content/pages/*.md` and `content/navigation.json`** is clever but adds a hard dependency on a personal access token (`GITHUB_TOKEN`, `GITHUB_REPO`). Page edits in production trigger a rebuild via Vercel's GitHub integration; that round-trip is ~60s of staleness. Acceptable for low-frequency edits, but document the failure modes in `docs/ARCHITECTURE.md` (currently mentioned briefly).

- **`is_chapter_admin()` PG function is correct but unused in practice.** With every admin write going through service role, RLS is effectively only protecting against bypass via a leaked anon key — not against a misbehaving authenticated session. Keep RLS on as defense-in-depth, but acknowledge in `docs/SECURITY.md` that _the application layer_ is the real enforcement boundary.

### Refactor opportunities

**(a) Extract `requireChapterAdmin(resourceFetcher, getChapterId)` and a single `withAdminAction` wrapper.**

- _Current problem:_ Every action calls `requireAdmin` then re-implements try/catch + `logAuditEvent` + `revalidate*` + permission checks (or skips them — see #1).
- _Proposed:_ A higher-order function that takes a resource resolver and a writer. Each action declares which resource it touches; the wrapper handles auth, audit log, error wrap, and revalidation tags.
- _Why better:_ Forces chapter scoping by construction. Halves the LOC in `lib/actions/`.
- _Migration:_ Start with one action (e.g., `updateEvent`), prove the API, port the rest module-by-module.
- _Risk of doing it:_ Medium — touches every admin write path; hidden audit log details may differ.
- _Risk of not doing it:_ The chapter-scoping bug stays one missed `if` away.

**(b) Replace the three near-identical registration outcome blocks with a single helper.**

- _Current problem:_ `registerForEvent` (lines 540-665), `registerForPermanent` (915-1023), and `completeRegistrationWithRider` (1267-1395) repeat membership-warning email construction and revalidation.
- _Proposed:_ `finalizeRegistration({ event, rider, membershipResult, ... })` returning the email payload + revalidation tags.
- _Why better:_ One place to fix the next email bug instead of three.
- _Risk:_ Small — paths are well-tested.

**(c) Promote chapter and membership configuration to a single typed config module.**

- Combine `REAL_CHAPTER_SLUGS`, `chapter-config.ts`, `vp-emails.ts`, ACP recipient (#4) into one `chapters` constant of `Record<DbSlug, ChapterConfig>`. One source of truth.

**(d) Move the cron handler to a Supabase Edge Function or pgcron job.**

- Currently GitHub Actions calls `/api/cron/complete-events` hourly. This works but the workflow has no failure alerting, no rate limiting on the endpoint, and the entire heavy lifting runs in a Next.js serverless invocation that may exceed Vercel limits as the catalog grows. A pgcron + RPC approach would be cheaper and observable.
